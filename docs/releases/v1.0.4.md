# NeoAlarm v1.0.4

`v1.0.4` is the location-alarm and reliability-hardening release.

The headline feature is location alarms: NeoAlarm can now trigger when the device enters a configured destination radius, which is aimed at transit use cases like waking up before a bus or train stop. This release also includes a large cleanup pass across the native alarm engine, location-alarm internals, release artifacts, and mission UX.

## Highlights

- Added location alarms with destination search, draggable map pin setup, radius presets, native geofence registration, and normal NeoAlarm ringing/mission handoff after arrival.
- Added location-alarm health states so missing location permissions, disabled location services, unarmed geofences, Play Services issues, and already-inside-radius cases surface visibly instead of failing silently.
- Added a hybrid location trigger model: inner geofence for arrival, outer geofence for approach assistance, and passive fused-location checks near the destination to reduce missed or delayed transitions without running constant GPS polling.
- Added location-alarm repair guidance on the dashboard when an enabled location alarm needs attention.
- Replaced the earlier map/search experiment with a cleaner provider boundary using MapLibre rendering, OpenFreeMap Liberty map style, Photon search, and optional OpenCage reverse geocoding for dropped pins.
- Tightened the release pipeline so GitHub releases publish universal APKs, ABI split APKs, app bundles, checksums, build metadata, and detailed checked-in release notes.

## Location Alarms

Location alarms are now a first-class alarm type alongside time alarms.

The setup flow supports:

- searching for a destination
- selecting a search result and closing the result list cleanly
- dropping or adjusting a map pin
- jumping the map to the device's current location
- choosing an explicit trigger radius
- warning when the device is already inside the selected radius
- saving the alarm into the same dashboard and ringing model as normal alarms

The Android side owns the actual trigger path. Flutter handles setup and UI, while native Android persists location-alarm records, registers geofences, receives transitions, deduplicates triggers, and starts the same foreground ringing service used by time alarms.

## Reliability And Health

This release does not treat geofencing as magic. Location alarms now have explicit readiness and failure states, including:

- ready
- re-arm pending
- no foreground location permission
- no background location permission
- location disabled
- geofence not armed
- waiting for the device to move outside the destination radius
- Play Services unavailable
- battery restriction warning
- low location confidence

Reboot and package-replace recovery now re-arm location alarms through native retry scheduling instead of assuming one registration attempt will always succeed. Passive foreground checks also help detect cases where the device is already inside a destination but the original geofence transition was delayed or missed.

## Map And Provider Stack

The map/search layer is intentionally modular so the provider can be swapped without rewriting the alarm model.

Current stack:

- MapLibre for map rendering
- OpenFreeMap Liberty for the default map style
- Photon for place search
- optional OpenCage API key in settings for dropped-pin reverse geocoding

The alarm record stores the final label, latitude, longitude, and radius rather than provider-specific IDs.

## Alarm UX Improvements

- Alarm cards are more compact by default and can expand for details.
- Alarm ordering is stable, so cards no longer jump around just because another alarm is now the soonest.
- `Skip next` now has an undo path instead of forcing users to disable and re-enable an alarm.
- Snooze summaries now say `minutes` instead of the confusing `min` copy.
- Location and time alarm labels were tightened to reduce box-in-box visual clutter.
- Timezone copy was removed from overview cards when it is not useful.
- The location-alarm setup screen now keeps global readiness diagnostics in settings instead of consuming setup-screen space.

## Mission And Playback Polish

- Math missions keep the answer field focused across problem transitions, reducing keyboard drop/flicker while solving consecutive questions.
- Custom tone display now truncates long filenames instead of overflowing the editor UI.
- Custom tone import and playback behavior remains protected by MIME checks, file-size limits, app-managed imports where possible, and fallback-to-bundled-tone behavior if the selected tone disappears.
- Volume ramp and extra-loud behavior are documented as combinable: ramp controls the `MediaPlayer` instance volume while extra loud applies a conservative speaker-only native boost when eligible.

## Engineering Hardening

- Decomposed large native location-alarm code paths into smaller coordinator, registration, readiness, approach-monitor, and re-arm scheduler components.
- Split alarm-engine method-channel handling for permission/status commands and tone commands.
- Added strict Dart analyzer settings for casts, inference, and raw types.
- Added app metadata as a single source for version/build/user-agent strings.
- Added tests for app metadata, location search, location setup behavior, smoke coverage, alarm specs, and math mission focus behavior.
- Updated architecture, sprint, testing, and review docs to match the current implementation.

## Release Artifacts

The release workflow publishes:

- universal signed APK
- `arm64-v8a` signed APK
- `armeabi-v7a` signed APK
- `x86_64` signed APK
- signed Android App Bundle
- SHA-256 checksum manifest
- build metadata
- ProGuard/R8 mapping file when available

For direct phone installs, the ABI split APK is much smaller than the universal APK. Most modern Android phones should use the `arm64-v8a` APK.

## Known Limits

- Location alarms depend on Android location services and Google Play Services geofencing. If location is disabled, background location is missing, or Play Services is unavailable, the alarm will show an unhealthy state and may not trigger.
- Underground travel, tunnels, weak network conditions, and approximate-only location can delay or prevent location transitions. Larger radii are safer for buses and trains.
- Location alarms are still intentionally scoped as a practical MVP, not route-aware transit automation.
